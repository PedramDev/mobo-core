## PERF05 — Parent Finalize batch cost and row revision safety

- Before: `process_batch()` read all owner `parent_finalize` payloads and `replace_map()` after each drop, claim, or commit, plus a full read after each Woo side effect, then another status read. For batch size `B` and `N` queued parents this incurred repeated map materialization; ordering is by serialized payload `queuedAt`, **not** SQL `created_at`.
- With the row table ready, require complete Default-only cutover first, load one owner map at the start, collect due items and `uasort` the immutable `queuedAt` snapshot once. Newly enqueued items during the unlocked Woo mutation wait for the next run; final status reads the current map once (including newly inserted items). The historical pre-cutover fallback and 5,000-item enqueue eviction remain separate.
- `Work_Queue_Store::replace_key_if_hash()` performs an owner/queue/dedupe/full-key/hash CAS claim transition, refuses an active competing claim and verifies the exact new row; it never upserts an absent row. `finish_claim()` uses the stored claimed payload hash **and** claim token for success deletion or retry/backoff replacement. Drops use `delete_key_if_hash()`. A newer re-enqueue supersedes an old claim; stale processing cannot erase the newer payload or clear its pending meta. SQL/corrupt snapshot/failed cutover/readback returns checkpoint-failed rather than success.
- This is **not** fully indexed parent due enumeration: `has_due_work()`, `get_status()`, queue-capacity eviction and batch start/end still walk whole maps. No DDL/payload rewrite or speculative created_at ordering conversion. Expired 120-second claim overlapping a long Woo sync remains a live runtime proof boundary.

## PERF06 — Primary Order Submission row operations and bounded head page

- Before: enqueue and token cleanup loaded/replaced the entire Connection-owned primary submission map; the runner materialized all rows before processing 1–5 orders and read it again for remaining-status. The independent Recovery queue had already been bounded in PERF04.
- When the row store is ready, enqueue uses one `put()` under the **existing** Connection-scoped DB advisory lock; cleanup checks the current queueToken **and the original page payload hash** under the same lock then does CAS deletion. A newer payload survives even when its token happens to equal the old token.
- Primary selection calls the existing `first_rows_checked('order_submission', 16)` (`max(16,limit+1)`), preserves database `id ASC` ordering and validates the whole selected page before exposing any item. Invalid head rows are CAS-cleaned. A full 16-row page conservatively indicates possibly hidden primary work: Recovery/legacy Woo fallback is **deferred** until the primary head becomes exhaustive, preventing unseen primary rows from being overtaken by a duplicate emergency marker. Additional primary rows, if any, are reached in subsequent passes.
- `count_strict()` replaces the end-of-batch full map; a negative/failed count produces `queue-read-failed`, `remaining=true`. The read-only admin queue probe is fail-closed on DB or migration failure because it guards explicit manual order retry. The same primary queue is never silently remapped to Default on missing owner.
- Payment, Wallet, per-order purchase lock, route fingerprint, mixed-order rules, error/retry policy and actual Portal HTTP are unchanged. An old primary item already removed by a newer worker is treated conservatively; real Classic/HPOS and 2-process MySQL tests are still outstanding. Recovery queue's own bounded/read-hash semantics from PERF04 remain in force.
