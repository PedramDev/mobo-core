# UX52–UX53 — large-catalog page-cache invalidation and warmup (30K+ per Connection)

Release: Mobo Core `10.34.16` (UX53; builds upon UX52 `10.34.15`). Separate candidate from the UX51 (`10.34.14`) Plugin Gate build; do not swap plugin on sites participating in frozen UX51 gate. Re-pin successor Suite to 10.34.16 first.

## Invariants

1. A product mutation first invalidates the applicable object/product cache. A warmup can be admitted **only after a recognized page-cache integration reports successful targeted purge**. Failed/absent integration never initiates speculative GET.
2. Variation changes use the parent WooCommerce product ID. Within one Connection, a stable `product:<id>` dedupe key represents a URL that can change when the permalink changes. The Source/Connection context is derived server-side. Another Connection with the same WordPress product ID cannot claim/delete these rows.
3. Both lanes (`cache_warmup_hot`, `cache_warmup`) live inside the existing indexed `mobo_work_queue` table. Enqueue, claim, CAS completion and due-query do not load/replace the whole queue map. Legacy UX51 URL-keyed rows are retired *after* a stable product-key upsert succeeds. The UX51 option-map import is Default-owner-only, bounded to 100 rows per slice, checkpointed, insert-if-missing (never replace_map) and retried by Cron even if the new queue initially has zero rows. The admission hint is invalidated on each attempted slice.
4. Claims are atomic on `(connection_id,queue_type,dedupe_hash,dedupe_key,payload_hash,claim_token)`; re-enqueue assigns a fresh revision and invalidates the old claim. A slow GET cannot consume the new revision. Expired claims become reclaimable after a worker crash. Each HTTP request holds a sitewide recovery-pipeline lease; a shorter enqueue mutex is released during GET.
5. A bounded installation-wide rate admission defaults to a minimum 1s gap between GET starts, with pipeline concurrency = 1. The gap can be filtered within 0–3 seconds by a trusted integration (`mobo_core_cache_warmup_min_gap_seconds`). Existing Cron pressure controls and configured batch (default 2, hard cap 10) still apply. No direct HTTP fetch is made during ordinary Product Sync.
6. A positive HTTP 200 is *not* claimed as a confirmed page-cache HIT unless the cache/CDN response header explicitly reports HIT. MISS/unknown are reported as unverified attempts (they may prime the cache). `private`, `no-cache`, `no-store`, `BYPASS`/`DYNAMIC` are not called cacheable success; GET redirects remain same-origin and limited.
7. Admission is capped at 20,000 rows per Connection across both lanes, with WARM capped at 18,000 (at least 2,000 slots reserved for HOT). Capacity overflow returns `queue-capacity`; **no unseen eviction** occurs. Re-enqueue of an existing key is still allowed when full. At/near the capacity threshold, the indexed DB aggregate is rechecked. Admission counters are aggregated once per Purger flush.
8. No unbounded list of URLs, product IDs or queue payloads is exposed in Health; it shows HOT/WARM counts, due, claimed, retry, oldest age, last GET result and admission counters. An installation-wide summary sums up to 100 Connections with `truncated=true` when applicable.

## Selective admission (default)

- `mobo_core_cache_warmup_policy = selective` is an installation setting. Product with `total_sales > 0` is WARM; a product with no known sales is COLD and **not prewarmed**. Historical sales are deliberately not labeled HOT or treated as recent-traffic analytics. COLD products remain correctly purged and can regenerate page cache on first ordinary visitor request.
- Real visit/sales analytics may classify HOT/WARM/COLD with the **trusted server-side** filter `mobo_core_cache_warmup_product_tier` (receives `$tier,$product_id,$reason`). HOT gets the dedicated due lane first; after 4 HOT slots, a due WARM receives a chance, avoiding starvation. WARM has a minimum 90s debounce; HOT retains the configured debounce (15s default).
- `all` mode admits every changed product as WARM for compatibility. With 30K products, `all` can hit the 20K queue cap and produce extensive traffic; use only with deliberate resource provisioning. No initial 30K crawl is scheduled merely because the plugin was installed.

## Deferred archives and WP Super Cache exception

The existing archive queue stores at most 5,000 distinct product IDs per deferred interval. UX52 now persists a sticky `productOverflow` marker when more IDs are supplied. With WP Super Cache active, overflow executes its available `wp_cache_clear_cache()` fallback, which can invalidate its **entire page cache**. This is intentionally explicit rather than falsely treating the truncated 5K IDs as a complete targeted purge. If the fallback is unavailable/fails, archive queue remains retryable and Health exposes `requiresSitewideFallback`; operators should investigate integration capability. Other supported page-cache integrations retain their existing targeted archive-URL paths. This exceptional full purge must be pressure-tested before a 30K all-products sync.

## Operational and test policy

- Start with `selective`, GET gap >= 1s, batch size = 2, and concurrency = 1. Monitor site load and the HOT/WARM queue age. Do not increase capacity/rate just to force all 30K items into cache.
- Tests: model-only 30K COLD mutation smoke, stable parent/revision/claim races, two-Connection isolation, deferred archive overflow, real MySQL queue index/CAS/30K/60K fixtures, and page-cache header differences. Real MySQL/WAMP and page-cache runtime tests are recorded as pending in `admin-ux-test-backlog.md`, not represented as proven by PHP syntax checks.
- No new custom-storage table or automatic database DDL is added by this release. Work queue needs existing `queue_dedupe`, `queue_due` and `queue_object` indexes.

## UX53: dispatcher, query and cache-safety contracts

- **Two Connections (30K each):** the general dispatcher continues all foreground work as before, but page-cache warmup uses `mobo_core_cache_warmup_dispatch_cursor_id` independently. A selected eligible Connection gets at most one warmup stage/GET per multi-Connection dispatcher invocation. Other due Connections get their turn on the next run; one global rate/lease controls actual GETs. In a single-Connection installation, existing stage/batch policy is retained.
- **Cheap due check:** `has_due_work()` and the real-Cron option preflight use indexed `LIMIT 1`, not full-map hydration or two per-check aggregate COUNTs. Aggregate SQL remains deliberately available for infrequent Health/snapshot pages.
- **Migration:** UX51 Default-only legacy map transfers in bounded, idempotent 100-row slices under the same enqueue/claim lock. Its source option is deleted only after the last successful slice; an interrupted slice replays safely. Existing product rows, including opposite HOT lane, supersede the legacy revision. Import invalidates capacity hints even on an interrupted slice. No cross-Connection adoption is permitted.
- **Admission:** WARM has an 18K cap, total HOT+WARM a 20K cap, regardless of 30K/60K mutation waves. At pressure, count using indexed SQL; DB count/update failure must reject a new row. Retrying a pre-existing row remains possible without evicting older work.
- **HTTP and privacy:** GET is anonymous (`cookies=[]`) and limited to the current product's same-scheme/same-origin canonical permalink. Unpublished and arbitrary cart/account/login/action URLs are rejected. Redirects may not change the canonical product target. `Set-Cookie`, `Vary: Cookie/Authorization/*`, `Cache-Control: private/no-cache/no-store`, cache bypass/dynamic and non-HTML responses are rejected for warmup success. Explicit cache-provider HIT is evidence; MISS/unknown are unverified, not fabricated HIT. WP Rocket, LiteSpeed and WP Super Cache response handling still require true integration testing.
- **No unsupported variants:** this implementation intentionally does not introduce multilingual, multicurrency or user-session cache variants. First real anonymous visit regenerates an intentionally COLD product after purge.
- **Release gate:** UX51 r8.3.177 frozen Suite must not be run against UX53 until exact plugin fingerprints and planned regression cases are updated. Real disposable MySQL/MariaDB stress and provider-specific WAMP tests remain unexecuted in this packaging environment.
